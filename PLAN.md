# Build Plan — Filter (IKEv2 + transparent SSL inspection)

This document is the contract for what gets built. Every requirement we
have agreed on through the project so far is enumerated, and every
component is mapped to the requirement(s) it satisfies. Nothing else
gets built without an update to this document.

> **Rule of engagement.** Once you (the user) sign off on this doc,
> implementation proceeds in the phases below. Each phase ends with a
> concrete deliverable you can verify. I do not make architectural
> changes mid-phase without re-opening this document.

---

## 1. What we are building, in one paragraph

A managed content filter for Apple devices (Mac and iPhone). The admin
runs a small dashboard on a server they control. From that dashboard
the admin creates a **profile** for each device they want to filter.
Each profile has its own set of rules (blocklist, allowlist, default
inheritance). The dashboard generates a `.mobileconfig` file the admin
delivers to the target device. **Installing the profile is the only
step the target device needs.** No extra apps, no manual settings, no
toggles. After install, every byte of internet traffic from the target
device flows through an always-on VPN to the server. The server
decrypts inspected HTTPS using a CA whose root cert is bundled in the
same profile, applies the rules for that specific profile, and either
forwards the traffic or returns a custom block page. The profile is
removable only with the admin-issued removal password.

## 2. Hard requirements

These are non-negotiable. Every requirement is checked off in section 5
when the corresponding component is described.

| ID | Requirement |
|----|-------------|
| R1 | Cross-platform — works on macOS and iOS, identical install UX |
| R2 | Single-step install on the target — one `.mobileconfig` file, nothing else |
| R3 | No app installed on the target device, ever |
| R4 | Cannot be removed by the device user without the admin's password |
| R5 | Profile UI is generated by our dashboard, with a custom per-device ID |
| R6 | Filtering happens at our server, with rules the admin set per-profile |
| R7 | Real network inspection at the URL level (path + query, not just hostname) |
| R8 | Custom block page rendered over HTTPS (no browser TLS warnings) |
| R9 | Catches all traffic — TCP, UDP, QUIC, IP literals, Electron, system services |
| R10 | Per-profile blocklist + per-profile allowlist + shared default blocklist |
| R11 | Live rule updates — change a rule in the dashboard, takes effect within ~1s, no reinstall |
| R12 | Cert-pinning apps (banks, Apple services, Signal, WhatsApp, etc.) keep working |
| R13 | Tamper-resistant against non-admin users on the target device |
| R14 | Scales — one server port handles many profiles, identification is automatic |
| R15 | Server runs locally on the admin's Mac for development, on a Linux VPS in production, with the same code |
| R16 | Dashboard already-built (DB schema, auth, per-profile rules editor) is reused, not rewritten |
| R17 | Removal password storage / surfacing in dashboard already-built is reused |

Out of scope (explicitly):
- Tamper-resistance against an attacker with **admin** rights on the target device. That requires MDM enrollment via Apple Business Manager. We don't do that.
- Filtering on Android, Windows, Linux. Architecture extends but is not built in this plan.
- Per-app filtering policy (e.g., "block reddit.com only inside Safari"). Domain-level only.

## 4. What runs where

### Admin's Mac (development / "VPS for now")

Runs everything except the target device:
- Backend API (Node, port 4000) — already exists
- Static dashboard (Node http.server, port 5173) — already exists
- SQLite DB at `backend/data/filter.db` — already exists
- **strongSwan (new)** — IKEv2 server, UDP/500 + UDP/4500
- **mitmproxy (new role)** — transparent mode, listening on `127.0.0.1:8080`, fed by pf rules
- **pf rules (new)** — redirect VPN-egress TCP/80,443 → mitmproxy; drop UDP/443

Setup is one shell script:
```bash
./setup-server-mac.sh    # brew install strongswan; configure; load pf rules; install mitmproxy addon
```

The admin runs this once. They never edit anything by hand.

### Target devices (Macs the admin wants to filter, future iPhone)

Run **nothing**. They install one `.mobileconfig` from the dashboard.
After install:
- Their IKEv2 client (built-in to macOS/iOS, no app) maintains a tunnel
  to the admin's Mac on UDP/500 + UDP/4500.
- Their CA trust list includes our CA (added at System scope so all
  apps trust it).
- Their System Settings has Network/Profiles/Security panes locked,
  and the profile is marked non-removable without the password.

That is the entire target-side story.

### Future production deployment

The same `setup-server-vps.sh` (Linux variant of the Mac script) runs
on a $5/mo VPS instead of the admin's Mac. The dashboard's "server
host" config flips from `<admin's-LAN-IP>` to `vpn.youdomain.com`.
Existing profiles get re-issued (new IKEv2 cert pointing at the new
endpoint). Nothing about the architecture changes — only the host the
target device dials.

## 5. Components and how they meet requirements

### 5.1 The `.mobileconfig` (target device)

Exact payload structure (validated in Spike A — `spike-a.mobileconfig`
lints clean and the embedded PKCS#12 decrypts to a per-device IKEv2
cert signed by our CA). The full set:

| Payload | Purpose | Requirement |
|---------|---------|-------------|
| `Configuration` (root, `PayloadScope=System`) | Forces device-level install. Shows admin password prompt on Mac. | R3, R4 |
| `com.apple.security.root` | The CA cert. Auto-trusted at System scope so all apps trust it without per-Keychain manual flip. | R8, R7 |
| `com.apple.security.pkcs12` | The per-device IKEv2 client identity (private key + cert chain), encrypted with a profile-baked password. | R5, R14 |
| `com.apple.vpn.managed` (`VPNType=IKEv2`) | The VPN config. References the PKCS#12 by UUID for cert auth. `OnDemandEnabled=true` with `Action=Connect` rule = always on. | R1, R2, R9 |
| `com.apple.systempreferences` | Locks `com.apple.preference.network`, `com.apple.preferences.configurationprofiles`, `com.apple.preference.security` panes (macOS only — iOS has equivalent restrictions implicit in profile install). | R13 |
| `com.apple.profileRemovalPassword` | The removal password, hashed inside macOS's own profile system. | R4 |

**Everything in this payload set is a documented Apple Configuration
Profile payload type.** Mac and iPhone speak it identically. This is
the same mechanism enterprise MDM uses every day.

### 5.2 strongSwan (server side)

IKEv2 server. macOS and iOS speak IKEv2 natively, so the target device
needs no extra client.

Configuration:
- Listens UDP/500 + UDP/4500 (IKE + NAT-T).
- Mutual cert authentication: server cert and per-device client certs
  all signed by our existing CA (`proxy-filter/server/ssl/ca.crt`).
- Hands out IPs from `10.10.10.0/24` to connecting peers.
- Each device gets a stable IP based on the cert's CN (we can pin
  this).

Per-device cert generation: when the dashboard creates a profile, it
shells out to a small script (`server/scripts/mint-device-cert.sh`)
which uses `ipsec pki` (strongSwan's own CLI) to issue a cert signed
by our CA. The cert + key + CA chain go into a PKCS#12 bundle that
gets embedded into the `.mobileconfig`.

Requirements satisfied: R1, R2, R3, R5, R14, R15 (same strongSwan
config works on Linux VPS or admin's Mac).

### 5.3 pf rules (macOS) / nftables (Linux)

The router that decides which packets go to mitmproxy and which get
NAT'd straight out.

Rules:
1. Inbound on the VPN interface, TCP dport 80 or 443 → REDIRECT to
   `127.0.0.1:8080` (mitmproxy).
2. Inbound on the VPN interface, UDP dport 443 → DROP (kills QUIC,
   forces browsers to fall back to TCP/443 which we then MITM).
3. Inbound on the VPN interface, anything else → NAT out via the
   normal egress interface.

A single pfctl-loaded ruleset on Mac, a single nftables ruleset on
Linux. Both checked into the repo under `server/pf.conf` and
`server/nftables.conf`.

Requirements satisfied: R7, R9, R14.

### 5.4 mitmproxy in transparent mode

The inspection layer. Validated in Spike B — running mitmproxy with our
existing CA, it correctly minted per-host certs and surfaced full URL
paths to its addon.

Configuration:
- `--mode transparent` — mitmproxy reads `SO_ORIGINAL_DST` to learn
  what host the device thought it was connecting to before the
  redirect.
- `--set confdir=server/mitm-conf/` — directory contains
  `mitmproxy-ca.pem` (concatenation of our existing `ca.key` + `ca.crt`).
- Loads `server/filter_addon.py` — described next.

Requirements satisfied: R7, R8, R12.

### 5.5 `filter_addon.py` (mitmproxy addon)

The decision logic. About 100 lines of Python. Hooks:

- `tls_clienthello(data)` — runs as soon as we have the TLS Client
  Hello with SNI. If the SNI is in the **exclusions list** (the 125
  starter entries from Spike D, extensible from the dashboard), set
  `data.ignore_connection = True` and mitmproxy passes the bytes
  through without decrypting. App keeps working, we lose URL
  visibility for that flow, we still see the SNI for logging.
- `request(flow)` — runs once per decrypted HTTP request. Identifies
  the profile by `flow.client_conn.peername[0]` (the source IP, which
  after IKEv2 decryption is the device's stable VPN-internal IP),
  looks up that profile's rules in `rules.json`, applies the
  precedence (allowlist > profile blocklist > default blocklist > allow),
  and either forwards or replaces the response with a 403 + our
  branded HTML block page.

Reads two files, both written by the dashboard:
- `server/rules.json` — `{ source_ip → { user_id, blocklist[], allowlist[] } }`
- `server/exclusions.txt` — one SNI domain per line.

Both files are watched by mtime; updates take effect on the next
request (~ms).

Requirements satisfied: R6, R7, R8, R10, R11, R12.

### 5.6 Dashboard (existing, modified)

The existing Node + SQLite backend and HTML dashboard. Surface stays
~95% the same (same auth, same per-profile rule editor, same
removal-password reveal). Underneath, three changes:

1. **DB schema delta.** The current `proxy_users` table gets renamed
   to `vpn_profiles`. Drop columns: `proxy_username`, `proxy_password`,
   `proxy_port`. Add columns: `vpn_ip` (stable internal IP),
   `cert_serial` (serial of the IKEv2 cert), `pkcs12_password` (random
   string used to encrypt the PKCS#12 inside the .mobileconfig).
   `removal_password`, `display_name`, `user_id`, `owner_admin_id` all
   stay.

2. **Profile create/delete shells out to `mint-device-cert.sh` and
   writes `rules.json` + `exclusions.txt`.** Same idea as the
   `ports.json` we wrote for the Node-proxy version, just different
   contents.

3. **Profile generator emits the IKEv2 .mobileconfig** described in
   5.1. This replaces the current HTTP-proxy + WireGuard variants.

The existing per-profile blocklist/allowlist UI, default blocklist UI,
exclusions list UI (new tab — shows the static list + dynamically
learned passthrough hosts), removal-password reveal, and request-log
viewer all carry over unchanged.

Requirements satisfied: R5, R10, R11, R16, R17.

### 5.7 What gets retired

The codebase is shrinking, not growing:
- `proxy-filter/server/proxy.js` (Node HTTP/MITM proxy) — gone.
- `proxy-filter/server/squid.conf`, `docker-compose.yml`,
  `passwd`, `ports.json` — gone.
- `proxy-filter/localtest/` (WireGuard local-test) — gone.
- `proxy-filter/admin/squidOps.js` — replaced by a smaller
  `vpnOps.js` (file writes for `rules.json` and `exclusions.txt`,
  shell out for cert minting).

What gets kept:
- `proxy-filter/server/ssl/` (the CA) — same CA, no regeneration.
- `proxy-filter/server/blocklists/` and `server/profiles/<id>/` —
  same on-disk format. Reused by the new addon.
- `proxy-filter/admin/db.js`, `router.js` — core kept, table schema
  migrated.
- `backend/` (the existing Node backend, dashboard auth, JWT) — kept
  as-is, just gets the new router mounted under the same
  `/api/proxy-filter/*` path (we'll rename the URL prefix in a later
  pass if you want).

## 6. Tamper resistance — who can defeat what

This is the part where I want to be precise so there are no surprises.

| Threat | Defense | Effective against |
|--------|---------|-------------------|
| Target device user **without admin** uninstalls the profile | `RemovalPassword` payload — Apple's own profile system blocks the uninstall flow without the password | ✅ Effective |
| Target device user **without admin** disables the VPN in System Settings | `com.apple.systempreferences` payload locks the Network pane on macOS; iOS has no user-accessible VPN toggle for managed VPNs | ✅ Effective |
| Target user changes their device's DNS to bypass us | Doesn't help — DNS is a side issue. All TCP/UDP packets go through the VPN regardless of which DNS server resolved them. | ✅ Effective |
| Target user installs a different VPN | macOS allows multiple VPNs but only one is active at a time. With OnDemand `Action=Connect` rule, ours wins on every connection. | ✅ Effective in practice |
| Target user uses a HTTP proxy through a service like Cloudflare WARP | Their alternative proxy can't establish a TCP connection because all TCP goes through us first. Same for any other userspace tunnel. | ✅ Effective |
| Target user with **admin / sudo** disables the VPN via Terminal | They can. `sudo ifconfig utun3 down` kills the tunnel; the OnDemand rule will try to re-establish but they can also `sudo launchctl bootout` the relevant agent. **Out of scope** — see Section 2. | ❌ Not in scope |
| Target user with admin uninstalls the profile via `profiles -D -F`  | The system still requires the password from the `RemovalPassword` payload. So no, even with admin shell access this should fail. | ✅ Effective (per Apple docs) |
| Target user installs a competing CA and uses it for evasion | They can install other CAs but it doesn't help them evade us — our VPN already has all their traffic. | ✅ Effective |
| Target user boots in Recovery Mode and tampers with the system disk | They can. Apple's only answer is FileVault + DEP/MDM enrollment. **Out of scope.** | ❌ Not in scope |

**The on-device install is a real "directory" — `/var/db/ConfigurationProfiles/` — owned by root, SIP-protected, and managed exclusively through System Settings or `profiles(8)`. A regular user cannot rm-rf it. An admin user is gated by the removal password for the un-install flow specifically.**

This is the same level of tamper-resistance that every enterprise MDM
profile gives you on a non-DEP-enrolled device. It is the
strongest protection achievable without ABM/DEP enrollment, which is
out of scope per Section 2.

## 7. Data flow walkthroughs

### 7.1 Admin creates a new profile

1. Admin clicks **Proxy Profiles → New Profile** in the dashboard,
   enters a name and user ID.
2. Backend `POST /api/proxy-filter/users` runs:
   1. Allocate next free VPN-internal IP from `10.10.10.0/24`.
   2. Generate random PKCS#12 password and removal password.
   3. Shell out to `server/scripts/mint-device-cert.sh <user_id>`
      which produces a per-device cert + key + PKCS#12 bundle,
      signed by our CA.
   4. Insert row in `vpn_profiles`.
   5. Write `server/rules.json` with the new profile's IP → empty
      rule set.
   6. Reload strongSwan (`ipsec rereadall`) and reload pf if needed.
3. Dashboard reflects the new profile in the Profiles list.

### 7.2 Admin downloads and installs the profile

1. Admin clicks **Download** on the new profile.
2. Backend `GET /api/proxy-filter/users/:id/profile` reads the cert,
   PKCS#12 password, removal password, and our CA, fills in the
   profile template (Section 5.1), and returns the .mobileconfig with
   `Content-Type: application/x-apple-aspen-config`.
3. Admin transfers the file to the target device (AirDrop, email,
   download).
4. Target device user opens it. macOS / iOS shows
   "Profile downloaded; review in System Settings."
5. They click **Install** → enter their Mac admin password (or in
   iOS's case, their device passcode).
6. Within seconds: VPN tunnel comes up, CA is trusted, settings panes
   are locked. Internet still works (everything is now flowing
   through our server) but it is now filtered.

### 7.3 Target device makes a request

1. Browser does `CONNECT example.com:443`.
2. Packet goes out the device's `utun` interface (the IKEv2 VPN).
3. Reaches our server, decrypted by strongSwan, source IP is
   `10.10.10.7` (the device's assigned IP).
4. pf redirects this TCP/443 to `127.0.0.1:8080` (mitmproxy).
5. mitmproxy reads `SO_ORIGINAL_DST` → learns the destination was
   `example.com:443`.
6. SNI is `example.com`. Not in exclusions.
7. mitmproxy mints a cert for `example.com` signed by our CA, does the
   TLS handshake with the device. Browser is happy because it trusts
   our CA (added by the .mobileconfig).
8. mitmproxy decrypts the inner HTTP request, sees `GET /` (or
   whatever).
9. `filter_addon.request(flow)` runs, looks up `10.10.10.7` in
   `rules.json`, finds it's user `sarah`, checks her allowlist
   (no), her blocklist (no), default blocklist (no) → allow.
10. mitmproxy opens its own TLS connection to the real
    `example.com:443`, forwards the request, streams the response back
    to the device.
11. Logged: `[ALLOW http] sarah GET https://example.com/`.

If the SNI had been a banking app's pinned domain:
- step 6 finds it in exclusions.
- step 7 sets `data.ignore_connection = True`.
- mitmproxy stops trying to MITM, just tunnels the bytes directly to
  the upstream.
- Banking app sees the real cert chain, all is well.
- We see `[passthrough] SNI=banking.example.com` and nothing else.

If the URL had been on Sarah's blocklist:
- step 9's lookup matches.
- mitmproxy returns a `flow.response = http.Response.make(403, ...)`
  with our 🛡️ block-page HTML.
- The browser renders the block page over HTTPS (no warning, because
  we forged a valid cert in step 7).

### 7.4 Admin updates a rule

1. Admin clicks **Settings** on Sarah's profile, adds `reddit.com` to
   her blocklist.
2. Backend writes the new entry to `server/profiles/sarah/blocklist.txt`
   and re-emits `server/rules.json`.
3. Within ~1s, mitmproxy's addon notices the file mtime change and
   reloads.
4. Sarah's next visit to reddit.com on her device → block page. No
   profile reinstall.

## 9. Honest residual risks

Things I cannot resolve in this document. They get resolved
empirically inside the phase where they manifest.

1. **iOS unsupervised .mobileconfig acceptance of the full payload
   combo.** I have validated each payload type independently (Spike
   A) and the combination lints. Real iPhone install is in Phase 5.
   If something blows up there, it would most likely be a
   Trust-Settings UX wrinkle — recoverable in a half-day.

2. **Specific Apple system services breaking despite the static
   exclusions list.** The static list is sourced from Apple's own
   enterprise networking guidance. The dynamic-passthrough mode in
   Phase 6 catches anything we missed.

3. **Captive portal on hotel/airport WiFi.** macOS and iOS both have
   `EvaluateConnection`-based On-Demand rules to allow captive portal
   detection traffic before VPN engages. They work in docs and in my
   experience but are network-dependent.

4. **Battery impact of always-on IKEv2 on iPhone.** Anecdotally
